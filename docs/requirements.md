# FHHS — Requirements

Derived from `docs/vision.md`. FHHS has no human users; the "role" in each
functional requirement below is one of its system actors (see
`docs/vision.md` → Target Users / Actors and `docs/use_cases.puml`).

## Functional Requirements (FR)

| ID     | Title                                | User Story                                                                                                                                              | Priority | Status      |
|--------|---------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|----------|-------------|
| FR-001 | Generate Proband Report               | As a Survey Platform, I want to request a personal cancer-risk report for a respondent so that the participant receives their own risk assessment.    | High     | Implemented |
| FR-002 | Generate Cancer Summary Report        | As a Survey Platform, I want to request a cancer-risk summary report for a respondent so that clinicians get a condensed risk overview.                | High     | Implemented |
| FR-003 | Generate Pedigree Report              | As a Survey Platform, I want to request a pedigree diagram report for a respondent so that the family structure and cancer history are shown visually. | High     | Implemented |
| FR-004 | Generate Family History Report        | As a Survey Platform, I want to trigger generation and delivery of the full family-history report so that the study site receives it without the participant waiting on it. | High     | Implemented |
| FR-005 | Retry Pending Family History Reports  | As a Scheduler, I want to periodically re-attempt family-history reports that haven't completed so that transient failures don't lose a report permanently. | High     | Implemented |
| FR-006 | Refuse Service Until the Survey Is Imported | As a Deployment Operator, I want FHHS to start against a database that does not yet hold the Family History Survey, or holds it without its reporting schema built, tell me in the log and on its readiness probe what to do (import it through Admin; have Survey build it), refuse report requests with that same message meanwhile, and become ready by itself once the import and the build land so that a fresh deployment never needs a restart or a seeded survey; and I want every report to read the survey's reporting schema under whatever name the site gave it, resolved at request time, so that a rename needs no restart either. | High     | Implemented |
| FR-007 | Authenticate the Calling Service     | As a Deployment Operator, I want FHHS to answer only callers that present the platform's service token, and to present it itself when it calls the Pedigree Drawing Service and its own report endpoints at addresses my deployment trusts, so that reaching the port is not enough to obtain a report. | High     | Implemented |

## Non-Functional Requirements (NFR)

| ID      | Title                          | Requirement                                                                                                                            | Category        | Priority | Status |
|---------|---------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|-----------------|----------|--------|
| NFR-001 | Service Caller Authentication   | 100% of REST endpoints require the platform service token, presented as `Authorization: Bearer <token>` and compared in constant time with `elicit.service.token` (environment `ELICIT_SERVICE_TOKEN`). Only what Quarkus serves under `/q/*` (the health probes) is outside the rule. With no token configured FHHS reports not-ready and answers every request 503; a configured token shorter than 32 characters fails the start. A request without the token, or with a wrong one, is answered 401 and no respondent data is read. The token is never written to a log, a trace or a response (UC-006). | Security        | High     | Implemented |
| NFR-002 | Non-Blocking Report Generation | The `/familyhistory/generate` HTTP call must return in under 2 seconds; the PDF/XML generation and SFTP upload it triggers must run asynchronously in the background. | Performance     | High     | Verified |
| NFR-003 | Pending Report Recovery        | Any family-history report execution left in `FAILED` status (not yet uploaded, and with fewer than 50 tries) must be retried by the scheduled sweep, which runs every 15 minutes. A report stuck in `STARTED` (e.g. the process crashed mid-generation) is not picked up by the sweep. | Availability    | High     | Verified |
| NFR-004 | External Call Observability    | 100% of calls to the external pedigree-drawing service must be wrapped in an OpenTelemetry client span recording status code and latency. The span records the payload's length, never its content (NFR-009). | Maintainability | Medium   | Verified |
| NFR-005 | Pedigree Service Timeout       | Calls to the external pedigree-drawing service must time out and fail gracefully (report still generated, with a placeholder) after 15 seconds. | Availability    | Medium   | Verified |
| NFR-006 | Report Traceability            | 100% of family-history report execution records must carry a non-null respondent ID and externally-issued study ID (XID), so every generated report can be traced back to the respondent and study it was produced for. A delivery with no XID now fails instead of being filed under a placeholder name (NFR-012); the execution record itself is still created without the check. | Maintainability | High     | Open |
| NFR-007 | Verified SFTP Destination      | A report is uploaded only to an SFTP server whose host key matches one the deployment configured (`family.history.sftp.knownHosts`); with no key configured the connection is refused. Turning verification off takes an explicit setting and is logged as a warning on every connection. | Security        | High     | Verified |
| NFR-008 | No Diagnostic Endpoints        | FHHS exposes no endpoint whose purpose is inspection or debugging. Every REST resource path is the entry point of a use case in `docs/use_cases/`; liveness and readiness are answered by the standard probes under `/q/health` only. A test fails the build when a resource path is not on that list. | Security        | High     | Implemented |
| NFR-009 | No Respondent Data in Logs     | No log record, at any level, carries an external ID (XID), a name, a date of birth, contact data, an access code, an answer, a report payload, the XML metadata content or a delivery file name. A record identifies its subject by respondent ID and describes work by kind, size and count. A test captures the log of a pedigree report and of a delivery and fails if such a value appears. | Security        | High     | Implemented |
| NFR-010 | Errors Explain Without Internals | A response body, a readiness check or a report never carries an exception message, SQL text, a JDBC address or an internal host name. The caller gets a fixed sentence and the HTTP status; the detail is logged with the respondent ID. A request with no body, or with a respondent ID that is not positive, is answered 400. The UC-005 instruction is the one deliberate exception and contains only the survey key and what to do. | Security        | Medium   | Implemented |
| NFR-011 | Output Encoding                | Every value FHHS places in report HTML that it did not author itself (answer text, the name of an "other" cancer, step names) is HTML-encoded; the markup FHHS writes around it is not. The PDF carries the same text unencoded. A test supplies markup characters through each such field and finds them encoded in the HTML and unchanged in the PDF table. | Security        | High     | Implemented |
| NFR-012 | Delivery File Names            | The two delivered files are named `<XID>.pdf` and `<XID>-index.xml` and are written in the configured directory only. A delivery whose XID is missing or blank, is `.` or `..`, or contains a path separator or a control character fails before anything is generated or uploaded. For every other XID the file names are exactly what they were before this rule. | Security        | High     | Implemented |
| NFR-013 | Report Service Timeout         | A call to a report the survey lists (UC-004 BR-004) waits at most 5 seconds for the connection and 60 seconds for the answer, the bounds Survey puts on the same call. A report that does not answer in time is handled like any report that could not be obtained: its section of the PDF says so and the remaining reports are still assembled. A test calls an address that never answers and gets the error section back. | Availability    | Medium   | Implemented |
| NFR-014 | Respondent Scope               | A report or a delivery is produced only for a respondent of the Family History Survey (`family.history.survey.key`). A request naming a respondent of another survey, or an ID no respondent has, is answered 404 with one fixed sentence before any report data is read (UC-006 BR-009). Each accepted request is logged with its path and the respondent ID only. A test asks all four endpoints for a respondent of another survey and for an unknown ID and finds 404 and no data read. | Security        | High     | Implemented |

## Constraints (C)

| ID    | Title                     | Constraint                                                                                          | Category    | Priority | Status |
|-------|----------------------------|------------------------------------------------------------------------------------------------------|-------------|----------|--------|
| C-001 | Runtime Platform          | Backend must run on Java 25 (`maven.compiler.release=25`).                                           | Technical   | High     | Verified |
| C-002 | Application Framework     | Backend must be built on Quarkus 3.40.x (LTS).                                                       | Technical   | High     | Verified |
| C-003 | Database Platform         | System must use PostgreSQL, sharing the `survey` schema owned by the Elicit Survey application.      | Technical   | High     | Verified |
| C-004 | Data Access Layer         | Data access must use Hibernate ORM with Panache (active-record entities) — not jOOQ.                 | Technical   | High     | Verified |
| C-005 | External Pedigree Service | Pedigree diagram rendering requires an external R/Kinship2-based HTTP service reachable at the configured `pedigree.url`. | Technical   | High     | Verified |
| C-006 | Deployment                | Must be deployable as a Docker container alongside Survey, Admin, and PostgreSQL via `docker-compose`. | Operational | High     | Verified |
| C-007 | Terminology               | The credential a respondent enters to reach a survey is the **access code** (`survey.respondents.access_code`, `Status.accessCode`, the `{AccessCode}` XML placeholder). "Token" is reserved for the question-text placeholder (`survey.relationships.token`) and must not be used for the respondent credential. | Business    | Medium   | Implemented |
| C-008 | Survey Arrives by Import   | No migration seeds the Family History Survey, its report definitions or its post-survey action; a deployment imports `family-history-survey.elicit` through Admin. FHHS recognizes the survey by its key (`family.history.survey.key`) and finds its post-survey action by key, never by an assumed id. | Operational | High     | Implemented |
| C-009 | Survey Text Depends on Survey's English Possessive Tidy | Question 40 (`What was {<S1>|}'s age at death?`) puts the possessive outside the placeholder, and relationships 95, 99, 103 and 107 fill `S1` with the bare pronoun `her` or `his` for the four grandparents (section-questions 101, 105, 109, 113). The text only reads correctly because `QuestionManager.replaceTokens` rewrites `" her's "`/`" his's "` (`QuestionManager.java:238-249`). Two consequences: that tidy cannot be removed from Survey without re-authoring this question and those four rules, and the pronoun values do not translate — Spanish collapses `her` and `his` to `su`, losing the distinction. The fix for both is to move the whole noun phrase inside the braces (`{<G1>'s maternal grandmother\|your maternal grandmother}`), matching the shape the other 24 rule values already use and the one translators need. Not scheduled. | Business | Medium | Known |
| C-010 | One Platform Service Token | The service token is deployment configuration shared by Survey, Admin, FHHS, Pedigree and Author (`ELICIT_SERVICE_TOKEN`, at least 32 characters). FHHS mints, stores and rotates nothing; rotation is a coordinated restart of every module. FHHS sends the token only to the origin of `pedigree.url` and to the origins listed in `elicit.service.trusted-origins` (`ELICIT_SERVICE_TRUSTED_ORIGINS`), compared by exact origin, and follows no redirect on a call that carries it. The Quarkus security extensions are not used for this: the check is a request filter, and no resource carries a role annotation. | Operational | High     | Implemented |
